# Parallel Subagents

Dispatch a user-supplied task list to at most N parallel subagents. Each subagent works in its own clone under `.subagents/`, on its own branch, and delivers by pushing that branch. Merge is always a human (or explicitly authorized main-agent) action — this skill never merges.

**N is a parallelism cap (to avoid freezing the machine), not the task count.** Wave size is `min(N, T)` where T is the number of tasks.

## Trigger and input

- Start only on explicit user request (slash command or an unmistakable "dispatch subagents in parallel" instruction).
- The trigger message must contain: a task list (one task per line) and N.
- If N is missing, ask once: "How many subagents should run in parallel?"
- If the task list is missing, ask once for it. **This skill only consumes a task list the user provides** — task decomposition happens before the trigger.

## Preflight checks (all mandatory, in order)

1. **git repo**: not a git repo → stop and ask the user what to do.
2. **remote**: no pushable remote → stop and ask the user.
3. **push access**: verify push permission (e.g. `git ls-remote origin` succeeds) → otherwise stop and ask.
4. **dirty main checkout**: uncommitted changes in the main checkout → stop and ask: commit first / stash / clone as-is. Default recommendation: commit first.
5. **.gitignore**: if `.gitignore` does not already ignore `.subagents/`, append it before doing anything else.

Each check must pass, or the user must explicitly direct you to continue past it.

## Prepare clones

- Reuse idle clones under `.subagents/` when available; clone fresh from the current project only if idle clones are short of the wave size.
- Exactly `min(N, T)` occupied directories during a wave.
- If idle clones exceed the needed count, use only what the wave needs and leave the extras as they are unless the user says otherwise.
- Each clone excludes `.subagents/` (no recursive clone) and `.git/` of the source (avoid nested-repo accidents). Clone what is committed; dirty-checkout handling was already settled at preflight.

## Dispatch (wave execution)

**Branch convention**: every subagent branch is `subagent/<task-slug>-<short-id>`.

- `task-slug`: take the task line, lowercase it, turn whitespace and `_` into `-`, drop every character outside `[a-z0-9-]`, collapse runs of `-`, then truncate to 40 characters. If nothing survives (e.g. an all-CJK task line), fall back to `task-<index>`, where `<index>` is that task's 1-based position in the list.
- `short-id`: 6 lowercase hex characters, generated by the subagent itself.
- Branch names stay unique across waves: a clone reused in a later wave gets a fresh branch name. Before committing, the subagent runs `git ls-remote origin "refs/heads/$BRANCH"` and regenerates `short-id` if that branch already exists.

Wave execution:

- Split the task list into waves of at most N tasks.
- Within one message, launch the wave as N parallel Agent tool calls, each with `run_in_background: true`.
- Each subagent prompt MUST instruct:
  - `cd` into its assigned `.subagents/<dir>` as its working directory;
  - create a branch following the branch convention above, based on the **current checked-out branch HEAD** of the main repository (unrelated existing changes do not affect branch base selection);
  - keep every commit on that branch — the main branch stays read-only for subagents;
  - when done, commit its own changes, **push its own branch only**, and report its final branch name back to the main agent;
  - stay inside its own `.subagents/<dir>`: it never writes to another `.subagents/` directory, and it leaves merging and the main branch to the main agent.

## Wave lifecycle (release → gate → refresh)

**Release criteria (per subagent)** — mark a subagent's directory released ONLY when all three hold:

1. Its Agent call has returned (process ended).
2. Its remote branch exists — verified by the main agent via `git ls-remote origin "refs/heads/$BRANCH"`, where `$BRANCH` is the branch recorded for that subagent.
3. Its working directory has no uncommitted changes.

If any criterion fails: report it to the user and keep the directory occupied. Release it only after the user says how to proceed.

**Wave gate** — the next wave starts as soon as all released subagents of the current wave have pushed their branches (gate = push, not merge). Merge does not block the next wave; the user interleaves merges at their own pace.

**Between waves** — for a released idle clone: `git fetch`, switch back to the main branch, and hard-sync to the latest, once the release criteria are met. Reuse that clone in the next wave; clone fresh only when no valid idle clone exists.

## Delivery and merge

- Delivery = pushed branch. This skill never merges.
- Merge is performed by the human, or by the main agent only after the user explicitly authorizes it in a given turn.
- On merge conflict: stop and report, and leave resolution to the user. The skill only guarantees branches are clean and mergeable, not conflict-free.

## Branch cleanup

- After the user confirms a branch is merged, ask once: "Branch <name> confirmed merged — delete local/remote copy?" — and delete only on approval.

## Safety constraints

- Every delete, overwrite, or cleanup of a directory, change, or branch requires the user's prior confirmation.
- Directory occupancy is trackable and distinguishable within the session as **occupied** or **idle**.
- Create only as many active clones as the current wave needs.
